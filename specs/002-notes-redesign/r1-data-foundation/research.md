# Decisions and verification boundaries

## R1 identity, R2 creation and R3 recovery

**Decision.** Accept a client-selected record ID: exactly 15 lowercase ASCII letters or digits. R2 generates it once per new draft using a cryptographically secure random source and keeps it through retries. Persist it as the primary key. An ordinary duplicate POST is a validation failure, not an update. No new idempotency endpoint or database of requests.

**Evidence.** PocketBase documents optional caller-supplied IDs on record creation, and the existing entries migration has this exact ID pattern. The [pinned 0.40.1 record tests](https://github.com/pocketbase/pocketbase/blob/v0.40.1/apis/record_crud_test.go#L1909-L1990) reject 14/16-character examples and accept a 15-character ID. The public docs describe a newer release; the acceptance test targets the repository’s 0.40.1 image. [PocketBase Records API](https://pocketbase.io/docs/api-records/) · [Existing ID field](../../../pb/migrations/1792384947_created_entries.js)

**Lost acknowledgement.** R3 retains the original submitted snapshot separately from the latest local edits. After an uncertain create or update, fetch by the same ID as the same account. Recognize an acknowledgement only when the stored writable content and expected resulting revision match that snapshot. Then send any newer local edits against the confirmed revision. If an owned record differs, preserve the draft and enter conflict handling. An inaccessible ID never authorizes an overwrite. Never turn an arbitrary 400 or 409 into success. If no record is visible after an ambiguous network outcome, a repeat create may use the **same** ID. A confirmed collision that cannot be reconciled requires an explicit failure, without automatic creation under another ID.

**Falsifier.** POST with known ID, ignore the successful response, replay that POST, fetch as owner and count. Require one note at revision 1 and the original body. Race two creates using that ID and require exactly one successful creation. Race two updates at revision 1, expecting one success, one 409 and only the winning body at revision 2. Include a different owner attempting the same ID. Record actual duplicate error details. If the pinned build rejects valid supplied IDs, stop R1 acceptance and revise this contract before R2. Server-generated-only IDs cannot identify an unacknowledged create.

## R1 folder equality and R4 literal search

**Decision.** Keep original spelling for display. Define the comparison key as canonical Unicode normalization (NFC), locale-independent uppercase, then NFC again. Trim folder names before computing their key. Use a binary unique index on owner plus key. The same key operation on the original searchable text and the literal search term supports non-ASCII comparisons without relying on database collation. Accents are significant; this is a specified casing algorithm, not linguistic matching for every locale. The search companion is derived alongside original text at R1 so R4 can read existing notes immediately.

**Evidence.** In a read-only in-memory SQLite 3.53.1 baseline, accented equality under NOCASE and Cyrillic LIKE both returned false; ASCII LIKE returned true. This was not a PocketBase runtime test. SQLite documents these defaults. [Collations](https://www.sqlite.org/datatype3.html#collating_sequences) · [LIKE](https://www.sqlite.org/lang_expr.html#like)

**Falsifiers.** In R1 try Café / CAFÉ / decomposed Cafe plus combining acute, and Москва / МОСКВА. Within one account only one spelling may commit, including simultaneous requests; another owner may use it. Café and Cafe remain distinct. Save a note containing “Маяк” and “café” split across adjacent formatting marks. Read back original and normalized text and verify an owner-filtered match with differently cased terms on pinned PocketBase. R4 repeats via the actual search interface, includes literal percent/underscore, rejects JSON node-name matches and tests snippet positions using original text even when normalization changes length. If the hook runtime lacks normalization or produces divergent keys, resolve that before accepting R1; never silently fall back to ASCII. An ICU extension or FTS adds packaging costs and does not address original-text highlighting.

## Provisioning and lifetime

**Decision.** Use the user model’s successful insert inside the creation transaction to create its default Notes folder before commit. Wrap the users model create/execute continuation in a transaction, pass its app into the continuation, and insert the default immediately after the user insert with that same app. Test rollback by inducing a default-folder validation failure on a disposable instance. [Pinned record event dispatch](https://github.com/pocketbase/pocketbase/blob/v0.40.1/core/record_model.go#L93-L114) Do not use an after-success notification that runs after commit: a failure there could leave a usable account without its folder. A partial unique index also prevents two defaults per account. Exercise public signup with its flag enabled, seeded users, and administrative creation of an ordinary user; a superuser itself does not receive a notebook. The empty-database assumption excludes a migration over existing production accounts. Test signup-disabled behavior separately.

**Decision.** Guard every active note’s folder and attached files inside the same write transaction as the note. In R1 refuse direct hard deletion of notes, default folders and nonempty folders. Otherwise an owner-only delete rule would still permit permanent loss or an active note without a folder. Empty custom folders may be deleted. R5 introduces recoverable transitions. Existing entries keep their own validator and rules.
