# R5 record lifecycle

## Stored state and write set

Keep the [R1 note fields](../r1-data-foundation/data-model.md), the [R4 comparison key](../r4-search/data-model.md) and stable note IDs. An active note has an empty PocketBase date and one real folder owned by its user. A retained note has a server deletion instant and either its original owned folder or an empty optional relation. Recently Deleted is a view. It never becomes a folder record.

| Successful write | Preconditions inside the write transaction | Exact changes |
|---|---|---|
| Ordinary create / edit | Existing R3 active-note validation, revision and R4 derivation | Existing write set. A content edit advances revision and the normal PocketBase edit timestamp. |
| Move | Active, submitted current revision, different real destination owned by the writer | Set folder to destination, revision +1. |
| Delete one | Active, submitted current revision | Set deleted to the current server instant, revision +1. Retain folder. |
| Delete custom folder | Owner, nondefault, confirmed snapshot matches all linked notes | All active members get one shared deleted instant, empty folder, revision +1. Previously deleted members get empty folder and revision +1, keeping their original deletion instant, including expired ones awaiting purge. Remove the folder in the same transaction. |
| Restore | Deleted, submitted current revision, server now strictly before deadline | Clear deleted, set folder to surviving original owned folder or the unique permanent Notes folder, revision +1. Missing/ambiguous default is an invariant failure and rolls back. |
| Daily purge | Deleted and at or past deadline on transactional reread | Permanently remove that note. Delete its attachment records only when no surviving note references them. Log the exclusive object keys and let PocketBase's post-commit worker remove the bytes. |

For the three individual transitions and bulk folder removal, preserve every unlisted note column byte-for-byte, including created, updated, body, title, text, search_key, tasks, open_tasks, user and ordered attachments. The library orders by last content edit. A metadata change must invalidate a stale editor without promoting the row in that order. Use a bound, allowlisted SQL UPDATE for these few columns inside PocketBase's transaction. Include user, id, observed revision and required state in its predicate, require one affected row. Use the ordinary record APIs for physical folder/file/note deletion. Clear every folder reference **before** deleting the folder, so PocketBase has no residual relation to rewrite. Raw metadata SQL emits no model after-update or realtime event. Refresh initiating views on acknowledgement. Other clients see current state on their next read or revision-checked save.

## Clock and purge progress

Use the raw SQLite TEXT column for lifecycle decisions. Select id, owner, revision, folder and deleted through the transaction's bound query before a note action, content PATCH or folder snapshot. A PocketBase DateField getter can return the empty string for corrupt nonempty text. For an existing row only stored `''` is active (the schema is NOT NULL). Do the same raw check on an authorized direct detail read before exposing it to the editor. A bad row logs its ID and yields a generic integrity error (500) without a write. On individual actions, owner lookup and the revision precondition still come first. An invalid folder member aborts preview/confirm for the whole folder.

A nonempty stamp must be exactly 24 ASCII characters in `YYYY-MM-DD HH:mm:ss.sssZ` form. Match the entire shape, replace the space with T, and require finite Date.parse plus exact equality with new Date(ms).toISOString() converted back to the stored form. Thus February 30 and alternate offsets fail. Use one UTC server sample per transaction and 2,592,000,000 elapsed ms. Equality with the deadline is expired. [Engine checks and SQL validation](research.md#deadline-and-comparison-engine)

The daily `expired-notes` job runs at `17 3 * * *` UTC. Capture runNow once, bind cutoff = runNow minus 2,592,000,000 ms as canonical UTC text, and assign a unique run ID. Read pages of up to 100 raw (deleted,id) pairs in ascending order with the bound predicate in [research](research.md#active-pages-and-purge-candidates). Start the cursor at ('','') and advance to the **last examined stored tuple**, including invalid, skipped and concurrently removed rows. Never restart from the batch head or use OFFSET. For each candidate open a short transaction and reread its raw value. Skip a missing or now-ineligible row. Log an invalid row by ID and continue without touching it or its attachments. Require the validated deletion instant ≤ cutoff, equivalently deadline ≤ runNow. A second keyset pass over the range above cutoff reports only malformed values using the same canonical SQL predicate as trash; it never purges that range. Both scans stop on an empty page. Concurrently inserted earlier keys wait for the next daily run.

For an eligible note, copy its attachment IDs and delete the note in the transaction. Deduplicate the IDs, reread each attachment and apply the existing unfiltered `attachment-cleanup.js:isReferenced(tx,id)` to **all** remaining notes, including other retained and expired notes. Keep referenced attachments. For each exclusive attachment record, take its real collection ID, record ID and stored file field. Inventory its exact `baseFilesPath()/` keys through PocketBase's configured filesystem (close it), including the expected original and any existing thumbnail keys. Emit one structured private info log per exact key before tx.delete of the attachment, with run ID, note ID, owner ID, attachment ID, prefix and key; emit the note event with an empty key list if all references survived or there were none. Before removal require PocketBase log retention enabled, the info/error levels retained and data size sufficient for each bounded event. If prerequisites are missing, emit a process error identifying the logging configuration and stop before deleting any note. The standard logger batches output, so the contained gate polls the private logs API for persisted entries. Use ordinary PocketBase record deletion. If discovery or a database operation fails, roll back this note, log the failure and keep the cursor advancing. The next run can revisit a surviving note. Record successful completion only after both scans drain, with run ID and counts for removed, invalid, skipped and failed rows. Distinguish incomplete/failed runs.

### Physical files and operator cleanup

The pre-delete log identifies intent even if the transaction rolls back. After commit PocketBase independently deletes each exclusive attachment prefix. Its error log includes the prefix and error and can arrive after the job completion log. Correlate `Failed to delete storage prefix` with the recorded prefix and exact keys. An API 404 or a successful database commit cannot establish byte removal. After a worker failure, leftover bytes are unreachable through the app but remain in private storage until an operator cleans them. No durable retry or new collection. [Contained storage proof](quickstart.md#live-api)

W6 T013 owns the manual procedure in `deploy/OPERATIONS.md`. Locate the purge event and matching worker errors in private logs, confirm the instance/bucket, and stat the logged keys using private storage credentials. For cleanup quiesce writers, including restores, imports, file uploads and other instances sharing the store. Recheck the committed note/attachment absence, all surviving note references without an active filter, and current records owning that ID/prefix against the same authoritative database. If any row/reference/key has been reused, ownership is uncertain, or storage inspection fails, leave the object intact. With writers still quiesced remove only individually verified logged keys, never a prefix sweep. Independently stat each key again, distinguish absent from denied/unreachable, record outcomes privately and resume service. Check surviving shared bytes. Where PocketBase logs are retained only briefly, review or export the correlated events before expiry.

## Migration and rollback

Add only `pb/migrations/1795000400_active_notes_and_purge.js`. Up changes the notes list rule from the R1 ordinary-users/owner expression to that expression followed by ` && deleted = ""`, and adds the nonunique partial index `idx_notes_purge` on `deleted, id` where `deleted > ''`. The other four notes rules, all folder/attachment rules and all existing fields/indexes stay as defined. The standard owner-only direct record view remains available by known ID for acknowledgement checks. The editor's active-only getNote rejects a deleted response. R3/R4 ordinary filters stay in place.

This migration is schema-reversible. Down restores the exact prior list rule and removes only this index. Check source or already-target metadata before each direction. Unexpected rule/index definitions abort the migration. Neither direction updates notes, recreates removed folders, revives writing or restores purged bytes. A binary rollback therefore needs a compatible backup to reverse actual user deletions. Prove schema reversal independently from product recovery, including every surviving row written **after** up.
