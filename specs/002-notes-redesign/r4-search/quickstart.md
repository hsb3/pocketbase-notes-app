# R4 validation guide

These are implementation gates. Run live services only through the project’s contained runner, on its disposable account and project volumes. Record the baseline and candidate commits, exact command, exit status and runner artifact paths. Require an empty container/network/volume cleanup report for each run. Every new regression assertion must first fail against the pre-feature behavior for the expected reason. Existing controls may already pass. Missing credentials, failed setup, skipped tests or an empty test selection supply no product evidence.

## Records API

Extend the existing real-client cases in `scripts/test-notes.ts`. Use real users A and B, an unauthed client, the fixture helpers and one additional owned folder. Use the exact marked request from the [contract](contracts/search.md). Inspect status, counts, IDs and the entire projected row shape, not just the HTTP code.

### Staged upgrade

Use `scripts/test-r2-upgrade.sh` inside `make test-api-contained`. Preserve its pre-R1 entries/default-folder replay and custom-field redaction checks.

1. **R3 baseline.** Stage through `1795000200_drop_entries.js`. Seed the Garden notes before loading the derivation hook, using the existing fixture technique. Retain the original untouched R1 note and folder. Add an active title-boundary row and a deleted twin, a NUL-only affected row with the exact fresh fixture above and R3 key `OAK\u0000LANTERN`, and a separate ordinary legacy row to edit later. Record fixed expected key strings independently of production helpers. Compare the complete stored bytes (e.g. `hex(CAST(text AS BLOB))` including the suffix), document contents and nonempty dates. Snapshot every column by ID, collection fields, all five rules, all index definitions and the R3 migration history. Filter the original one-note excerpt/redaction controls by their original ID. Keep a separate stopped R3 database copy for the failure case.
2. **First up.** Apply the new migration, verify its history entry, and check all note IDs, unchanged non-key columns, folder, fields and rules against the R3 baseline. The title fixtures gain exactly the expected prefix, the NUL-only key becomes `OAK\nLANTERN`, ordinary keys stay identical. Require exactly one additional collection index and matching SQLite `index_list` / `index_xinfo` metadata for `idx_notes_user_updated_id_deleted`: nonunique, nonpartial, key columns `user, updated, id, deleted`, DESC flags `0,1,1,0` and no extra key columns. Ignore the implicit non-key rowid entry. Preserve other indexes.
3. **Owner reads and writes under R4.** Start the staged R4 server. With the Garden owner's token require the exact fresh `ZE` and `LANTERN` IDs, marks, NUL context and zero cross-boundary totals. The deleted twin stays absent. Run the page-plan check below on the marked `LANTERN` request before adding more matches. As that owner POST a *new* affected note with `Ash\u0000wicker`; PATCH the designated ordinary legacy note, submitting its current revision and the 158-x title-boundary document. Require acknowledged revisions 1 and previous+1, independent owner GETs, correct R4 keys and original marks on both IDs. Snapshot all rows and metadata **after** the saves, including the new ID, exact body, title, text, revision, attachments, tasks and dates. Stop the server.
4. **Down, reapply and both no-write replays.** Use the pinned CLI with an empty hooks directory for offline migration/inspection. While R4 is applied, copy its unmodified file under `1795000301_replay_note_search.js` in the fixture migration directory. Install a disposable SQLite `BEFORE UPDATE OF search_key ON notes` trigger that aborts every such update. Run migrate up to apply the copy: verify its history entry, unchanged post-save rows and single index. Verify the trigger still exists, then remove it. For each down below verify the expected newest applied filename first, supply `y\n` to `migrate down 1`, and require its removal from history. Exit zero alone also permits a cancelled down. Never serve or auto-apply between down and inspection.
   - Down the **copy** to exercise the real down body. The index must disappear from both collection and SQLite metadata, with every other field, rule and index identical to baseline. For every ID compare every non-key column to its post-save value. Untouched rows must also equal their full pre-up R3 snapshots. For the new row require exact `ASH\u0000WICKER`, and for the edited row require `"X".repeat(158) + "ZÉ"`, derived from its current writing. Compare bytes beyond NUL. Retain this down snapshot.
   - Reinstall the aborting trigger. Down the **original** migration with rows and metadata already at R3. Require identical down snapshots, R3 migration history and a surviving trigger. Remove trigger and spare migration file. Apply the original up; require exact post-save R4 snapshots for all IDs, rules and index definitions, with no replay history entry. Restore the R4 hooks, repeat marked owner hits and cross-boundary misses (the edited row now also matches `ZE`). Run the existing `9999999999_replay_default_folders.js` controls last. All copies and triggers are fixture-only.
5. **Atomic failure.** In the separate stopped R3 copy, arrange an earlier sortable affected ID with its valid R3 key and a later NUL-affected ID with an unexpected stored key (`OAK\u0000WRONG`, sharing the legacy prefix). Check execution order by ID. Commit that fixture and snapshot every key as bytes, collection indexes, SQLite index definitions and history. Run the genuine up with empty hooks. Require failure identifying the later ID after the index and earlier repair would have been attempted. Reopen the database independently and compare the complete before/after snapshots. The earlier key, bad key, index metadata and migration history must all survive unchanged.

**Page query plan on the pinned engine.** In the staged server use `--dev` SQL tracing to a fixture-local file. Authenticate before taking the file offset and issue one marked page request with the synthetic owner and fixed ASCII term. Read only the trace segment for that request. Isolate the single paginated notes SELECT for its bound pattern, excluding the concurrent COUNT. Require the actual list-rule terms (users collection and owner ID), `deleted = '' OR deleted IS NULL`, the escaped contains pattern, both descending sort keys and limit 20. Preserve the entire observed SELECT structure, including projections and any aliases or nesting. Fail on missing, ambiguous or unexpected SQL. Dev output renders parameters for debugging. For this fixed fixture accept only a single read-only page SELECT with the known synthetic values, verify the whole statement shape and all literal values before explaining it. Use the existing staged superuser SQL API to run `EXPLAIN QUERY PLAN` for that statement against the **same** PocketBase database/SQLite engine. Require an owner seek using the exact new index and no temporary B-tree for any part of ORDER BY. Retain only the checked synthetic SELECT, SQLite version and plan rows. A simplified SQL lookalike, count plan, host SQLite result or metadata check cannot pass this gate.

## Browser behavior

Use the ordinary login, `ownerData`, `doc`, `seedNote` and owner detail reads from the existing test fixtures. In both Chromium and WebKit exercise 390×844, 810×1080 and 1440×1000 CSS pixels. Search from All Notes and from a custom folder different from the target note’s folder.

- Drive Search, paging, Clear and result opening with a keyboard. Check title, actual folder, visible nonempty mark, single matching link and plain-text handling. Test a direct search URL/reload, punctuation/numeric input, a late body-only hit, empty query, zero-hit message and return to the original nonfirst ordinary page.
- Create enough matches to open a row on search page 2 after scrolling. Test editor Back and browser Back independently. Assert restored path, q, both pages, exact result IDs, scroll offset and focused row. Open another result from the wide detail side list and verify Back. Check the bare note URL’s fallback. Refresh after save so a removed match disappears and focus has a valid destination.
- At wide width open one result and edit it, then select a different result. Hold a real PATCH in flight, release it and verify the owner’s new revision before the selection changes. Force a failed flush using R3’s request interception, exercise Keep editing, Discard and Save and continue with a successful real retry on separate attempts. Check URL, editor contents, focus and stored revisions at each boundary. At 390, exercise the guarded Back path from a dirty result before selecting another one.
- At **810 and 1440** on each engine run two detail-side cases, parameterized over Next/Previous, Clear and Escape in the search field. Start each attempt from an origin with ordinary page 2, a submitted multi-page search and a selected note whose saved edit keeps its query term. For Previous, Clear and Escape start on search page 2, for Next on 1. (1) Edit the note, force the real flush to fail and choose Keep editing. Assert the same detail URL/history index, submitted field, page, rows, dirty words and editor focus; an independent owner GET still has the old saved revision. (2) Edit again in a fresh attempt, hold the outgoing PATCH, check the detail stays selected, then release the successful save. Require exactly one PUSH to the origin folder, no selected editor, the intended query/page for paging or only ordinary page 2 for Clear/Escape, and focus on Search. Check the owner has the acknowledged revision. One browser Back returns to the same note with its saved words and **old** side-list query/page; editor Back then restores the original folder-search entry, scroll and row focus.
- Switch the query before a delayed prior response resolves and sign out/switch owners with a response pending. Release the genuine earlier response last. Verify stale rows never replace the latest results or disclose A’s title/folder/snippet to B. Force a failed list read, show error + Retry, then recover against the real backend. Distinguish these states from a completed empty list.
- In light and dark, verify 390 places the input below the scrollport and clear of Compose, and 810/1440 place it above. Compare bounding boxes, focus visibility, result mark contrast (text/background at least 4.5:1) and document scrollWidth against clientWidth. Capture the filled and empty states with controls visible. For the search profile, write one PNG per engine × width × theme × state under the browser container’s /tmp/r4-search-views, using all four dimensions in each filename. Copy the directory beside the JSON report before teardown and review all 24 captures. R6 owns physical keyboard, real-device and cross-device sign-off.

## SC-004 timing

One tagged test per width per Playwright project, one worker, zero retries. For each cell create a fresh A, its default folder and four custom folders. Write exactly 20 active notes in each using ordinary owner requests. Embed one distinct opaque term in the body of each of 20 preselected notes (four per folder), never in titles or folder names. Keep an independent manifest of expected ID, title, folder name, original match and adjacent context for each trial. Use common synthetic context for the other 80 notes and place each target past the first 120 body characters. Confirm folder count, active counts per folder, total 100 and all 20 distinct targets from independent owner reads before timing. Open an ordinary folder list and wait for its initial render.

1. For each of the 20 predetermined terms, start with the previous result cleared and the list ready. Install a page-side clock before input. Take `performance.now()` at the input event that supplies the complete term. Submit immediately with Enter through the real form. Include submit, navigation, the actual HTTP request, rendering and one animation-frame paint opportunity in elapsed time. Use the same browser clock at both ends (observe the matching row, then two requestAnimationFrame callbacks and confirm it is still visible). Do not prefetch or reuse cached results. Keep the other 19 samples when one is slow.
2. Finish only when exactly one visible result links to the expected ID and shows the expected title, folder, original marked term and adjacent context. Require a successful new records-list response for that query, the bounded projection, and zero unexpected detail reads. A wrong/missing result fails correctness even if 19 timings pass. A correct result at or beyond 2000 ms is a timing miss. Use the existing bounded test timeout and emit partial diagnostic evidence on failure.
3. Attach one JSON payload per cell to the Playwright result as inline bytes with attachment name `sc004-samples`, MIME `application/json`. Include engine, width, counts per folder, and 20 numbered samples with expected/actual synthetic IDs, term/mark, correctness and elapsed milliseconds. The contained runner copies the JSON reporter file to `test-results/<project>/sc004.json` on pass or failure and runs the stdlib checker. The profile runs both search specs; check all functional cases for pass/zero retries, and count timing cells only from the timing spec tagged `@sc004` (the Playwright JSON `spec.tags` value is `sc004`, matching the convention used by `scripts/check-sc003.py`). Require exactly the six expected engine/width pairs, one attempt per cell, all samples correct and finite/nonnegative, and **at least 19 strictly below 2000 ms per cell**. Reject duplicates, skips, absent samples, retry results and pooled scores. Print each cell’s 20 numbers, count under threshold, min/median/max. Retain the raw report with the measured summary.
