# R2 acceptance on disposable stacks

Run from the implementation worktree with Docker Compose v2.24.4+, Bash, OpenSSL, Python 3 and GNU timeout. The checked-out runner streams sources into a fresh capped container, builds the production app, creates private credentials, runs against shared loopback and removes the labeled containers, volumes and networks. Use these two commands for behavioral evidence.

```sh
make test-api-contained
make test-browser-contained
```

1. **Upgrade and API.** Apply the real migrations to fresh and staged upgrade databases. Include a user predating R1, a user already owning a default, a custom folder, an existing R1 note and synthetic old entries. Exercise the actual missing-folder operation twice, compare default IDs, and check each ordinary account has exactly one default. Confirm entries is absent, R1 note data and folders survive, and a new account still gets its default. As owner A, compare one page of 20 long notes with and without the R2 field projection on the same seeded stack. Record decoded UTF-8 JSON bytes and elapsed times under both projections. Require fewer bytes, exact row keys, body-only preview, 120-code-point cap, updated preview after edit and private A/B/anonymous results. Time is diagnostic. Keep the attachment write, byte/download, foreign-denial, deletion protection and real cron tests green.
2. **Capture and navigation.** Run both engines at 390, 810 and 1440 CSS px. Create Garden, type the two specimen lines, wait for Saved, then sign into a fresh, independent desktop context as the same account. Require exactly one row, exact first line, exact body and folder. Cover soft wrapping, a long title capped at 160 code points, blank first line, whitespace-only abandon, duplicate/reserved/blank folder input, All Notes default filing and a forbidden note deep link. Inspect actual list HTTP traffic, including absence of per-row detail fetches.
3. **Write ordering.** Hold the first real write response for three seconds after the server has committed. Continue typing while it is held, attempt Back, release the response and observe the one PATCH against revision 1. Back must complete only after the latest write succeeds. Assert the editor never briefly claims Saved for the pending generation, the second browser reads the final text, and the owner has one record. Also exercise a normal pause without navigation, rapid selection changes and one failed request with draft and error visible.
4. **Warm input (SC-001).** Use production assets at 390×844 with touch enabled. Start on the signed-in list with a fresh browser cache. Observe the production editor chunk requested and completed from the list before any note opens. This warms the sample without priming the editor by opening a note. Return to the list between trials in the same browser context. For each of 20 attempts per engine record browser-monotonic timestamps for the Compose tap (touch/pointer activation) and the resulting editor input. Tap Compose once. Send one real keyboard character on a fixed schedule, e.g. 500 ms from the tap, without a locator click, focus, fill, readiness wait or second key. Verify the input arrived in the focused editor within 1,000 ms and the final document contains that character exactly once. Late dispatch, missing/duplicate input, wrong target and late insertion count as misses. Each trial uses a new draft. Regular Back flushes or abandons it. Log all 20 durations/outcomes and denominator per engine to stdout even on failure, and require ≥19/20 independently. No retries or pooled results.
5. **Responsive proof.** At each width check the visible regions, active note, reachable Compose and Account, visible focus, theme contrast and document scroll width ≤ viewport width. With a scrolled second list page, Back restores the row and position. Resize a dirty note between widths and verify caret position and draft content survive. Capture light/dark screenshots for review, retaining successful evidence outside the disposable project. Physical keyboard/IME behavior, search, resilience and the two-minute owner journey have separate later gates.

Independently run the repository's static checks (`bun run lint`, `bun run knip`, `bun run build`, `bunx tsc -p scripts/tsconfig.json`, `python3 scripts/ai-context.py check`, `bun run docs:build`). A passing build alone cannot establish the scenarios above. Record the actual exits, SC-001 distributions, bytes/timings, width evidence, pre-cutover SHA and any unexercised operational scripts in the implementation PR. No release tag or deployment is part of R2.
